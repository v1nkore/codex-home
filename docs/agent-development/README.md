# Разработка с агентами: стартовый набор

Черновик для адаптации в рабочем репозитории. Он опирается на цикл из [видео о Software Factory](https://www.youtube.com/watch?v=5UP7ca7qSHQ): постановка задачи, реализация, независимая проверка, автоматические проверки и принятие человеком по уровню риска. Для передачи работы между сессиями используется карточка состояния задачи; оркестратор и автоматическое распределение задач не требуются. Набор не описывает существующий процесс компании и не даёт агенту доступов.

[Короткая и подробная схемы процесса](PROCESS.md) показывают этапы, действия человека и агентов, проверки и возврат на доработку.

## Где живёт каждое правило

| Слой | Содержание | Источник истины |
| --- | --- | --- |
| `AGENTS.md` | Короткий порядок работы агента и ссылки на документы | Репозиторий |
| Контракт задачи | Требование, инварианты, сценарии отказа, критерии приёмки | Задача или PR |
| Skill ревью | Повторяемый независимый разбор конкретного diff | Папка навыков Codex после адаптации |
| CI | Сборка, тесты, анализ, обязательные проверки именно того commit, который принимается | Конфигурация CI |
| Права и среда | Доступ к данным, секретам и выпуску изменений | Настройки платформы и учётных записей |
| Статус задачи | Текущий этап, актуальный commit, доказательства, блокер и следующий шаг | Одна карточка задачи в трекере; по умолчанию GitHub Issue |

## Порядок внедрения

1. **Пилот на одном репозитории.** Выберите ограниченный класс задач и владельца процесса. Перенесите адаптированный [`AGENTS.template.md`](AGENTS.template.md) в корневой `AGENTS.md`. Для 5–10 задач используйте [контракт задачи](TASK.template.md) и [карточку состояния](TASK-STATE.template.md).
2. **Доказательства к каждому изменению.** Агент прикладывает diff, проверяемый commit, результаты команд, список непроверенного и влияние на контракты и данные. Человек принимает задачу по исходным критериям. После правки кода проверки запускаются повторно.
3. **Независимое ревью.** Для значимых изменений попробуйте [skill ревью](../../skills/critical-change-review/SKILL.md) в отдельном проходе с исходной задачей и diff. Замечания проверяет автор изменения; ревьюер не переписывает код в том же проходе.
4. **Автоматические барьеры.** Закрепите подходящие проверки в CI и правило принятия только по актуальному commit. Для платежей и документооборота добавьте тесты на инварианты, повторы, конкурентность, частичный сбой, права и миграции там, где эти сценарии применимы.

После первых ревью собирайте [набор проверочных случаев](REVIEW-EVALS.template.md) из реальных пропусков и ложных замечаний. Перед сменой модели, инструкций или схемы ревью прогоняйте эти случаи снова: качество проверяющего агента тоже требует проверки.

## Состояние задачи без оркестратора

Одна карточка задачи — источник истины для всех сессий. В рабочем проекте это существующий трекер; если его нет, GitHub Issue по [шаблону состояния](TASK-STATE.template.md). PR хранит код и результаты проверок, а карточка ссылается на PR. Сообщения в чате сообщают о прогрессе, но не заменяют карточку.

Допустимые этапы: `уточнение → готова → реализация → проверка → ревью → ожидает принятия → принята → выпущена`. Из `проверка` или `ревью` задача может вернуться в `реализация`; `блокирована` и `отменена` доступны из любого незавершённого этапа. `Принята` означает решение человека по конкретному commit, а `выпущена` — отдельный факт релиза.

При смене этапа исполнитель обновляет карточку: текущий этап, время, владельца следующего действия, ветку и HEAD, проверенный commit, ссылки на CI и ревью, блокер и следующий шаг. После нового commit прежние результаты проверок и решение о принятии остаются в истории, но не подтверждают новую версию: задача возвращается к проверке и повторному принятию. Для статуса `ожидает принятия` нужны доказательства по актуальному commit.

Пользователь получает сообщение при значимом переходе или необходимости решения, например: `Этап: проверка · Сделано: обработка повторов · Проверено: unit и integration на abc123 · Далее: независимое ревью · От вас: действий пока нет`. По запросу «какой статус?» агент читает карточку и сверяет её с PR, а не отвечает по памяти чата.

Новая сессия сначала читает карточку, актуальный контракт задачи, PR и текущий HEAD. Если данные расходятся, она сообщает о расхождении и восстанавливает состояние до продолжения работы. Одновременно изменяет карточку один ответственный исполнитель; ревьюер оставляет замечания в PR, а исполнитель переносит итог в карточку. Это обеспечивает передачу контекста без автоматического запуска следующего агента.

## Решения человека по риску

- **Обычное изменение:** разработчик принимает diff и доказательства после CI.
- **Значимое изменение:** добавляется независимое ревью и проверка владельцем затронутого компонента.
- **Критичное изменение:** изменение денег, юридически значимых документов, прав, миграции данных или выпуска требует проверки доменных инвариантов и решения ответственного человека до выпуска. Конкретные владельцы и процедуры определяются командой.

Уровень риска определяется последствиями и затронутым поведением, а не числом строк diff. Эти категории надо согласовать с правилами компании; они не заменяют существующие approval gates.

## Как понять, что процесс помогает

Сравните первые 5–10 задач с последующими: долю задач, принятых без переработки; дефекты после принятия; время человека на проверку; число циклов ревью; полную стоимость принятой задачи. Раз в несколько недель обновляйте правила по найденным сбоям и убирайте шаги, которые не улучшают результат.

Пока нет фактических данных рабочего репозитория, здесь намеренно нет готового CI-файла, команд сборки, списка владельцев и политик доступа. Их следует брать из конкретного проекта, чтобы шаблон не выдавал вымышленные гарантии за реальные.
